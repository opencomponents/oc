# OpenComponents v1 — Re-architecture Plan

Status: Draft · Generated 2026-07-26 · Progress last synced against merged PRs 2026-08-01

**Legend:** ✅ Done · 🚧 In progress · ⬜ Not started

This document describes the **full re-architecture** we intend to ship as OpenComponents
`v1`. It is the "breaking swing": the changes that genuinely require a major version.
Non-breaking modernization (promise APIs added additively, internal ESM migration,
dependency hygiene) does **not** need to wait for v1 — it lands incrementally on the
`0.x` line first, so that v1 itself is mostly *removals* plus the opt-in modern runtime.

---

## 1. Guiding principle: the three breakage layers

Every proposed change is classified by **who** has to do work and how much. This ranking is
the non-negotiable frame for the whole release.

| Layer | What it is | Acceptability | Cost to user |
|-------|-----------|---------------|--------------|
| **Registry** | Everything about *running the registry*: the programmatic `Registry` API (`start/close/register`), plugins, storage/metadata/server adapters, registry config, the CLI, the `oc`/`oc-registry` packages | ✅ Most acceptable | You change the registry deployment and everything works |
| **App** | A consuming **web app**'s contact with OC: the **browser** `oc-client.js` (the `window.oc` API, `<script>` include, auto-injected importmap, `<oc-component>` markup) and the **node SSR** `oc-client` it imports | ⚠️ Acceptable if worth it | If you run 50 web apps you must update all 50 before they work again |
| **Component** | How an individual component is authored, compiled, packaged, rendered | 🚫 **Unacceptable to break** | A company with 3000 components would have to migrate all of them |

Two clarifications that drive the whole plan:

- **"App" is not the registry's programmatic API.** `new Registry(opts).start()`, plugins,
  and adapters are code that *runs the registry* — changing them is a **registry-layer**
  change, the most acceptable kind. Almost all of the modernization work lands here.
- **The browser `oc-client.js` contract is app-layer and is protected like components.**
  A web app embeds it via a `<script>` tag and renders `<oc-component>`. It must stay
  **fully drop-in**: no importmap burden, no `window.oc` API changes, no markup changes.
  The *only* intentional app-layer break in v1 is the **node SSR `oc-client`** going
  promise-only/ESM — a one-time update per SSR app.

Every change below is tagged `[REGISTRY]`, `[APP]`, or `[COMPONENT-ADDITIVE]`.

## 2. The frozen component contract (must never break)

These surfaces are **immutable** because ~3000+ already-compiled components have them baked
into storage and cannot be re-compiled:

- **`oc.files.*` shapes** in compiled `package.json`: `dataProvider {type,src,hashKey,size}`,
  `template {type,src,hashKey,version,minOcVersion,size}`, `static`, `env`, `imports`.
- **`oc.packaged` / `oc.date` / `oc.version` / `oc.container` / `oc.renderInfo` / `oc.parameters` / `oc.plugins`** semantics.
- **Data provider contract**: `module.exports.data = function(context, callback)` with
  node-style `callback(err, data)`.
- **The VM sandbox globals allow-list** exposed to data providers (`require` (wrapped),
  `module`, `exports`, `console`, `setTimeout`, `Buffer`, `Error`, `AbortController`,
  `AbortSignal`, `Promise`, `Date`, `Symbol`, `URL`, `URLSearchParams`, `crypto`, `fetch`,
  `process.env` subset).
- **The `context` object keys** passed to `data(context, cb)` (`action`, `acceptLanguage`,
  `baseUrl`, `env`, `params`, `plugins`, `renderComponent(s)`, `requestHeaders`,
  `requestIp`, `setEmptyResponse`, `staticPath`, `setHeader`, `setCookie`, `templates`,
  `streamSymbol`).
- **Auto-injected props** for no-data-provider components (`_staticPath`, `_baseUrl`,
  `_componentName`, `_componentVersion`).
- **Accept-header render modes**: `application/vnd.oc.rendered+json`,
  `application/vnd.oc.unrendered+json`, `application/vnd.oc.info+json`.
- **Legacy template runtime rendering** for bare `jade` / `handlebars` types (see §5.3).
- **Component name grammar** (`[a-zA-Z0-9\-_]`, not `_package`) and semver versions.

Anything not on this list is fair game for the registry layer.

## 2b. The frozen browser-client (app) contract (must not break)

A web app's only real coupling to OC is the browser client and the markup it drives. In v1
the browser `oc-client.js` stays **fully drop-in** — treated with the same protection as
components. The following are frozen:

- **Delivery / include**: served at the same URL (`{registry}/oc-client/client.js`) and
  usable via a plain `<script>` tag. No ESM module-script requirement, **no importmap the
  host app has to author** — the client keeps injecting the importmap itself
  (`oc-client.js` `type: 'importmap'` head injection).
- **Global**: `window.oc` remains the entry point with a stable public API
  (`oc.ready`, `oc.render`, `oc.renderByHref`, `oc.renderNestedComponent`, `oc.events`,
  `oc.build`, `oc.conf`, etc.).
- **Markup**: the `<oc-component>` tag and its attributes (`data-rendered`,
  `data-rendering`, `data-version`, `data-id`, `data-hash`, `data-name`) and the
  `oc:rendered` / `oc:error` events are unchanged.
- **ESM component loading** stays internal: the client resolves and `import()`s ESM
  component bundles itself; the host page does nothing new.

Browser-client internals may be modernized freely **as long as none of the above changes**.
This is the concrete answer to "will apps have to add an importmap or re-touch their
pages?" — **no**.

## 3. v1 pillars

**Registry-layer core (the bulk of the work — most acceptable to break):**
1. **Promise-first, callback-free registry API** — remove the `universalify` dual API. `[REGISTRY]`
2. **ESM-only registry packages with proper `exports` maps** — no CJS build. `[REGISTRY]`
3. **The HTTP server adapter becomes the real boundary** — hooks/config speak
   `OcRequest`/`OcResponse` instead of leaking Express types. `[REGISTRY]`
4. **Promise-only adapters + metadata store as source of truth** — drop the legacy callback
   storage-adapter shim; bundle a default metadata store; flat-file `components.json`
   becomes export-only legacy. `[REGISTRY]`
5. **Package split** — `oc-registry`, `oc-cli`, `oc-core`, with `oc` as a thin umbrella. `[REGISTRY]`
6. **Platform + config cleanup** — Node `>=22` for the registry; remove stale config knobs
   and the redundant CLI publish gate. `[REGISTRY]`

**Component layer (additive + opt-in only — never break existing components):**
7. **Opt-in modern component runtime** — ESM-native authoring with `async data(context)`
   and typed context, blessed as the default for *new* components. `[COMPONENT-ADDITIVE]`

**App layer (protect the web apps; one deliberate break):**
8. **Browser `oc-client.js` stays fully drop-in** — no app changes required. `[APP]` (guarantee)
9. **Coordinated node `oc-client` (SSR) v1** — promise API + TS types + ESM; the one
   intentional per-app update. `[APP]`

## 5. Notes on the trickiest surfaces

### 5.1 Why removing the CLI version gate is safe `[REGISTRY]`
The gate compares CLI `major.minor` to registry `major.minor` and rejects "old" CLIs. It
existed when CLI and registry were one lockstep package. Today publishing already validates
package structure, `node-version`, and `template.minOcVersion` (a real, per-template
forward-compat signal). The semver gate now only produces upgrade friction and would make a
`1.0.0` registry reject every existing v0.x publisher. Remove it; keep the substantive
validators.

### 5.2 Metadata-first without a config break `[REGISTRY]`
Bundling a default metadata adapter means existing zero-config registries keep working: they
transparently get the default store, and the flat-file export path keeps legacy file
consumers happy. Operators who already configured a metadata adapter are unaffected.

### 5.3 Legacy templates as an opt-in compat package `[REGISTRY]`
Old components identify their template by the bare strings `jade` / `handlebars`. The
runtime mapping and special-cased rendering **must keep working**. In v1 this moves out of
core into a dedicated compat package. Old components still render; operators serving them
install the compat package — a registry-config action, never a component migration.

### 5.4 Express as one adapter, not the contract `[REGISTRY]`
The `HttpServerAdapter` abstraction already exists but public hooks/config still leak Express
types (plus a global `Express` augmentation in the shipped types). v1 finishes the job: hooks
speak `OcRequest`/`OcResponse`, Express becomes a swappable adapter, and the Fastify adapter
becomes first-class. An Express-compat shim eases the one-time registry migration. **None of
this touches web apps** — it's registry-boot code.

### 5.5 The importmap question, answered `[APP]`
The browser client already injects the importmap itself. v1 keeps it that way: **web apps
never author an importmap or change their `<script>`/markup**. Any ESM push happens inside
the client and in the (opt-in) component authoring path, not in the host page.

## 6. Two-track sequencing

### Track 1 — `0.x` (non-breaking, ships continuously, now)
Land everything that can be additive so v1 becomes mostly *removals*:

1. ⬜ Add promise-returning variants of `registry.start/close/register`, plugins, adapters,
   and the node `oc-client` (keep callbacks working, emit deprecation warnings). — tracked in
   [#1528](https://github.com/opencomponents/oc/issues/1528) (registry `start/close/register`),
   not yet merged.
2. ⬜ Migrate registry internals to ESM incrementally. — not started.
3. ⬜ Introduce the modern component runtime as **opt-in** and make it the `oc init` default,
   while keeping legacy authoring fully supported. — not started.
4. ✅ Dependency hygiene: replace `colors` (unmaintained), drop unused `async`, audit ESM-only
   deps against the build, prune old callback micro-deps (`getport`, `read`, `try-require`,
   `nice-cache`). — done via [#1531](https://github.com/opencomponents/oc/pull/1531) (`colors` →
   `picocolors`, `async`/`@types/async` removed, ESM-dependency audit documented).
5. 🚧 Emit deprecation warnings for: callback APIs, `s3` shortcut, `refreshInterval`, boolean
   `discovery`, `oc.json` `mocks`, bare `jade`/`handlebars` on `oc init`, and the callback
   node `oc-client` API. — the central `deprecate()` utility plus warnings for `s3`,
   `refreshInterval`, boolean `discovery`, and `oc.json` `mocks` are **merged** via
   [#1532](https://github.com/opencomponents/oc/pull/1532) (tracked in
   [#1529](https://github.com/opencomponents/oc/issues/1529)). Still to cover: bare
   `jade`/`handlebars` on `oc init`, the callback registry API, and the callback node
   `oc-client` API.

**Additional registry-layer groundwork landed ahead of/alongside the plan above** (see §4.1
for detail): the `HttpServerAdapter` abstraction with Express (default) and Fastify adapters
(R3, ✅ done — [#1507](https://github.com/opencomponents/oc/pull/1507)–[#1513](https://github.com/opencomponents/oc/pull/1513),
[#1518](https://github.com/opencomponents/oc/pull/1518)); an opt-in pluggable metadata store
(R7, 🚧 in progress — [#1503](https://github.com/opencomponents/oc/pull/1503)); and monorepo +

[#1505](https://github.com/opencomponents/oc/pull/1505)).

## 7. Migration guide (for the v1 release notes)

**For web app owners (app layer):**
- **Browser-only apps:** nothing to do. Same `<script>`, same `window.oc`, same
  `<oc-component>`, no importmap to add.
- **SSR apps (use node `oc-client`):** update to the promise API (`await
  client.renderComponent(...)`), adopt ESM/types. A 0.x callback shim eases the transition.
  Keep Node `>=20`.

**For registry operators (registry layer):**
- `await` the now-promise-only `registry.start/close/register` and plugin/adapter APIs.
- Update imports for the package split (`oc-registry`, `oc-cli`, `oc-core`).
- Move to ESM (or dynamic `import()`); run the registry on Node `>=22`.
- Config: `s3` → `storage.{adapter,options}`; `refreshInterval` → `pollingInterval`;
  `discovery: true` → `discovery: { ... }`; `oc.json` `mocks.plugins` → `development.plugins`.
- If serving pre-`oc-template-*` components, install the legacy compat package.
- No metadata action needed (default bundled); configure an adapter for scale.
- Custom hooks receive `OcRequest`/`OcResponse`; use the Express-compat shim if needed.
- Publishing no longer rejects older CLIs on semver skew.

**For component authors (component layer):**
- Nothing required. Existing components keep working. To adopt the modern runtime, scaffold
  new components with `oc init` (ESM default) and use `async data(context)`.

**For plugin/adapter authors (registry layer):**
- Return promises from `register` / adapter methods (callbacks removed).
- Throw typed `Error`s.
